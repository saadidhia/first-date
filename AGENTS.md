# AGENTS.md

First Date على الطريقة التونسية: a two-player date game in Tunisian Arabic (RTL), built with TanStack Start, self-hosted with Docker Compose (Node server via Nitro, Postgres, Caddy).

## Architecture

- `src/routes/index.tsx`: landing page with create/join room forms. The host picks the room mode first (`src/components/mode-picker.tsx`): `date` (First Date, 2 players) or `friends` (صحاب, 2 to 7 players), stored in `rooms.mode`.
- `src/routes/room.$code.tsx`: the whole room experience (join gate, chat UI like Messenger, composer with suggestion chips, timer, private result card). A friends room shows as a group chat: a lobby with the host's start button, who already answered, and the group report. In the lobby the host sees an ✕ next to each other player to remove them (`kickPlayer`), only while the room is still waiting. Once a regular question is revealed in a group of 3+, a `RevealCard` shows every option with who picked it (name chips, a bar, 👑 on the majority), replies in their own words, who ran out of time, and a verdict line (everyone agreed, X alone against the group, everyone different, split). Rooms of two keep the chat bubbles. In a `date` room only, soft looping background music plays by default at a low volume (`src/components/room-music.tsx`, the file `public/romantic.mp3`): a header button turns it on/off, and it fades out and pauses while anyone is talking in the voice call (`voice.talking`), then fades back in. `ChatRoom` now owns the single `useVoice` instance and passes it to both `VoiceBar` and `RoomMusic`, so there's still one WebRTC connection.
- `src/lib/room.functions.ts`: all game server functions (`createRoom`, `joinRoom`, `startRoom`, `kickPlayer`, `spin`, `playJoker`, `getRoomPreview`, `getRoomState`, `submitAnswer`, `reportScreenshot`, `getMyResult`). `joinRoom` locks the room row to enforce the player limit (`MAX_PLAYERS`). `kickPlayer` lets the host of a friends room remove a player while it's still `waiting` (not the host, not themselves); the removed player's next `getRoomState` poll fails `authorize`, which the client turns into a "you were removed" screen (`removed` in `useRoomState`) and stops polling.
- `src/lib/questions.ts`: the question registry (Tunisian dialect), timings and `pickQuestionIds(mode, seen)`. Every question has exactly 3 options (the server accepts option index 0–2). It holds the hand-written classics (explicit ids) and expands the big themed banks in `src/lib/bank/` (compact format, see `bank/types.ts`; ids are `<category>_<position>`, so those files are append-only). 1000 questions in total (with marriage, votes and spins); the newest ones at the end of each bank are the bolder (still respectful) ones.
- Each room gets 30 questions. A date: 25 spread evenly over its core topics (money, sharing, family, cleanliness, cheating, freedom, fights, psych), then 5 random marriage questions shown in gold. Friends: 20 over their core topics (how you see your friend, situations, embarrassing, money, secrets, fights), then 8 votes and 2 private questions (`bank/friends-3.ts`, ids `vote_<n>` / `spin_<n>`, read with `roundFor(id)`; they have no options and no scores). On a vote everyone picks one of the others (stored in `answers.vote_for`); the counts only show in the report, never who voted for who. Before the first private question the host turns the wheel once (or it turns by itself after `SPIN_SECONDS`) and the server picks a random player; that same player gets both private questions (`rooms.spins`, question index → player id) and is the only one who answers, in free text; the answers only show in the report. Once per game they can play the joker (`playJoker`): the question is swapped for another `spin_` one and the timer restarts; `rooms.joker` keeps the index and the skipped question, shown crossed out in the report. A friends room of 2 can't vote, so `startRoom` swaps its votes for regular questions (`withoutVotes`). Older friends rooms ended with 5 `saraha` questions instead; the report still handles them. The browser keeps the ids it has played (`firstdate:seen` in localStorage) and sends them on create, so the next room picks unseen questions first.
- Questions are worded per player by `personalize()` in `questions.ts` (used by `questionFor(id, gender, partnerGender)`): `{شريكك}`/`{صاحبك}` follow the other player's gender, `{masc|fem}` is a word about the other player and `{@masc|fem}` a word about the player answering. In a friends group of 3 or more, `othersGender` returns `'group'`: `{صاحبك}` becomes صحابك and every friends template has a third, plural form `{masc|fem|plural}` (e.g. `{عندو|عندها|عندهم}`, or `{صاحبك|صاحبتك|واحد من صحابك}` when the question is about one person). A test in `group.test.ts` fails if a friends question misses its plural; new friends questions must include it. Options are first-person replies that must make sense alone (the chosen one is shown to the other player), so `submitAnswer` words them for the partner's gender before saving.
- `src/lib/compat.ts`: compatibility scoring and the private note (score, partner portrait, tips, per-topic matches, finale answers), with mode-specific wording. Used for 2-player rooms.
- `src/lib/group.ts`: the report for a friends room of 3 or more (`computeGroupReport`): my score with each friend, every pair ranked, one title per member, questions everyone agreed on, where I was alone, who picked the same answer as who, and everyone's finale answers. `computeRounds` gives the vote counts and spin answers, added to both report kinds.
- `src/lib/marriage.ts`: the final marriage report. Every date ends with 5 of the `MARRIAGE_QUESTIONS` (in `questions.ts` + `bank/marriage.ts`), worded differently for men and women; options are ordered partnership (0) → traditional (2) so both genders compare on the same scale. Partner answers to these stay hidden in the chat and only show in the report.
- Admin pages share `src/components/admin-shell.tsx` (login gate, tabs, logout). `src/routes/admin.tsx` (`/admin`, where you land after login) is the stats dashboard (players, active now, last hour, games per mode (date vs friends), the average match % of finished games (couples; every pair of friends) with how many fall in each band, a daily bar chart with period / type / players-or-games filters over the last 90 days, a daily table, the games someone was in during the last hour, newest game first so rows don't move on refresh). Every game row shows its match % (`matchOf` in `admin.functions.ts`, the same `computeCompat` score players see; a group shows its average and closest pair) once the players answered 3 questions together, and each player chip a mic: green when it's on (pulsing while they talk), red crossed out when they muted it, grey crossed out when they're not in the call (`useAdminVoice` polls `getAdminVoice` every 2 s); `src/routes/admin_.players.tsx` (`/admin/players`) lists who played with who: each game shows its two players linked by a pink (couple) or blue (friends) line (`src/components/admin-games.tsx`, data from `getAdminGames`), with a type filter and name search; `src/routes/admin_.funnel.tsx` (`/admin/funnel`) is the completion funnel (created → partner joined → played → reached the report) and the traffic sources, over a 7/30/90-day window (`getAdminFunnel`); the source is guessed by `trafficSource(referrer, userAgent)` in `src/lib/traffic.ts` and stored on `rooms.source` when the room is created (`createRoom` takes the page `ref`). `src/routes/admin_.messages.tsx` (`/admin/messages`) is the secret-message inbox, fed by `getAdminStats` in `src/lib/admin.functions.ts`. Protected by a signed session cookie (`src/lib/admin-session.ts`): login checks `ADMIN_EMAIL` / `ADMIN_PASSWORD` from env, the cookie is signed with `SESSION_SECRET`, and admin-only server functions call `getAdminEmail()`. There is no signup.
- Secret messages: `src/routes/sir.tsx` is a public page (`/sir`) where anyone can send the admins a message. Messages are anonymous: the form doesn't ask for an Instagram username (a link can't detect the account). The server only records which app the link was opened in (`source`, guessed from the in-app browser user agent, e.g. Instagram). Old messages may still have an `instagram` name. Stored in `secret_messages`. Server functions are in `src/lib/secret.functions.ts`: sending is public, with a global cap of 20 messages per minute and a honeypot; reading, marking as read and deleting are admin-only. The admin dashboard has a "الرسائل السرّية" section with the link (copy / share) and the inbox.
- Players pick a gender (`players.gender`, 'male' | 'female', nullable for old rows) before creating or joining a room.
- Voice chat: everyone in a room is in a group call (`src/components/voice-bar.tsx`, under the room header) from the moment they open it, waiting phase included, while the game runs and for 5 minutes after it ends (`rooms.ended_at`), then it closes for everyone. Players join as listeners (no mic, no permission asked); the bar has a single mic button (red = muted, nobody hears; green = everyone hears), the first tap asks for the mic. Every connection keeps an audio slot (transceiver) so the mic is put in with `replaceTrack`, without reconnecting. A reopened page sends a `hello` signal so the other side starts a new connection right away, and signals sent before the page joined are skipped. Audio goes straight between the players (WebRTC, every member connected to every other one; the smaller player id makes the offer). `src/lib/use-voice.ts` runs it in the browser; the server only relays setup messages through `voiceSync` in `src/lib/voice.functions.ts` (tables `voice_members`, who is in the call / muted / speaking, and `voice_signals`). Who is talking is measured on the audio itself in the call, and read from the server by players who didn't join. STUN only by default; set `TURN_URLS` / `TURN_SECRET` (the optional `turn` compose profile runs coturn) for networks that block direct audio.
- `src/lib/use-screenshot-guard.ts`: a best-effort screenshot deterrent and blur overlay.
- `src/lib/session.ts`: stores the per-room player token in localStorage.
- `db/schema.ts`: Drizzle schema (rooms, players, answers, events, voice_members, voice_signals). `authorize(code, token)` lives in `src/lib/room-auth.ts`, server only. Migrations live in `db/migrations` (applied by `db/migrate.ts`, run by the `migrate` compose service) and are generated with `npx drizzle-kit generate --name <name>`. Never edit applied migrations.

## Game flow (server-driven)

`rooms.phase` moves waiting → intro → question → reveal → … → done; the first spin question goes spin (waiting for the host) → spinning (the wheel animation, chosen player known) → question → reveal, the second one straight to question. A date leaves `waiting` as soon as the guest joins; a friends room stays there (others can still join) until the host calls `startRoom`, and can't be joined after. Nothing runs on a schedule. `getRoomState` (polled by both clients) calls `advance()`, which moves the room on once `phaseEndsAt` has passed. Every transition is a conditional UPDATE (matching on id, phase and current_index), so two clients polling at once can't double-advance. `submitAnswer` jumps straight to `reveal` when every player in the room has answered (on a spin, as soon as the chosen player has).

## Conventions / decisions

- UI wording: plain Tunisian, no unclear French/English loanwords. A room is called "لعبة" (not روم), the result is "التقرير السرّي" (not نوت), screenshots are "تصوير الشاشة" (not capture).

- Players are authorised by a random UUID token. Every server function checks it against the room code.
- The other player's answer text is never sent to the client before its question is revealed.
- The result is computed for the requesting player only, so each note stays private.
- Notes are phrased around "شخصية" (feminine noun) so they read naturally for any gender. Tunisian 2nd person ("إنتي", "تحب") is gender-neutral.
- Theme: a dark Sidi Bou Said night palette in `src/styles.css` (Tunisian red primary, `--gold`, `--sidi-blue`), with `--love-gradient` (red to gold), `.bg-love`, `.text-love`, `.btn-love` (gradient button with glow), `.surface` (raised card), `.eyebrow` (small gold label above section titles), `.bubble-mine`, `.zellige` and `.hero-shade`. The landing hero uses `public/wedding-hero.webp`; the flag is `src/components/tunisia-flag.tsx`. The `<html>` element is `dir="rtl"`, so use logical utilities (`ms-`, `me-`, `start-`, `end-`, `rounded-es-` …).
